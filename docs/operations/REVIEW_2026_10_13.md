## Priority findings

### 1. Neutral answers produce an unsupported personality label

`src/lib/assessment/career-engine.ts`, `scorePersonality`, chooses the second letter of every axis whenever its sum is zero. Twelve neutral answers therefore return INFP, although all eight letter weights equal 0.5.

A direct execution of the current engine reproduced INFP, “Inspirational Mentor,” and strengths including “Emotional intelligence” and “Deep focus & introspection.” These descriptions come from the chosen letters, not positive evidence from these answers. `scoreCognitive` also uses those letters to choose a profile, so the tie affects more than display copy.

Fix: represent tied/weak axes as uncertain; use continuous evidence for matching; suppress categorical strengths and styles when evidence is insufficient. Include a neutral-answer regression test that checks the actual output descriptions, not just weights.

### 2. The reasoning component largely shifts all career scores together

In `matchCareers` and `matchMajors`, `cognitive.score / 9 * 0.6 * 0.35` contributes the same amount to every candidate. Holding the cognitive profile fixed, moving from 0/9 to 9/9 adds 21 points to all unrounded, uncapped scores. It does not change their underlying relative order; rounding/capping can create ties. Candidate-specific variation comes from whether the career accepts the single cognitive profile. That profile changes at selected thresholds and also depends on personality letters.

A two-career execution reproduced 47/40 becoming 68/61 with the profile fixed. This is a demonstration of the formula, not a measured production-user outcome.

Fix: decide whether reasoning represents practice progress or career-specific evidence. If the latter, use justified dimensions and candidate requirements; if the former, show it separately and describe its role honestly. Audit ranking sensitivity across repeated balanced attempts before changing model weights.

### 3. Account recovery is still a public-launch blocker

The live interface confirms email recovery is unavailable. The code intentionally gates recovery behind `VITE_PASSWORD_RECOVERY_ENABLED`; the guard prevents a misleading success message but does not solve account recovery.

Fix: complete sender-domain/SMTP setup and verify a real external user's delivery, link handling, expiry and password reset before enabling the flag. Also check signup confirmation under the chosen production settings. Follow `docs/operations/AUTH_EMAIL_SETUP.md`.

### 4. Release confidence still has operational gaps

`docs/operations/PRELAUNCH_REPAIRS_2026_10_12.md` explicitly leaves backup/restore proof, lifecycle checks, consent review and load verification open. Export-tool tests prove parts of tooling, not recoverability of a real database and storage backup. Simulated migration tests do not prove current production permissions.

Fix: restore a protected backup into an isolated environment; verify an account/file lifecycle with disposable fixtures; complete the outstanding authenticated cross-account checks; validate a representative school workload. Record actual evidence and environment for each check. Keep historical checks separate from new verification.

### 5. Localized ABBI offers less career detail than English

The English server branch uses `generateAbbiReply`; Russian and Uzbek use a separate curated guide. In `localized-guide.ts`, a recognized career returns generic advice to try a project and talk to a practitioner. Translating the career name does not give that response the same career-specific depth as the English knowledge base.

Fix: share structured career content across languages and translate it consistently, or clearly constrain the localized feature's promise. Add representative intent/content tests, not only catalog-label coverage. ABBI should remain described as a curated guide.

## Product and usability observations

The homepage explains guest answering, free-account results, practical activities and the three sections. The live assessment reiterates that nine reasoning questions do not measure all ability. The methodology page discloses that independent predictive validation is not claimed. These are useful improvements.

The introduction repeats account/saving information and presents a long block before the start control. Shortening this into an overview plus optional details would make the first action easier to find. This is a usability judgment from the live content, not a conversion measurement.

Visual-choice-to-interest weights and the 40/35/25 combination remain authored heuristics. The reviewed documentation does not establish that these weights predict meaningful student outcomes. Keep the exploratory positioning and investigate usefulness through a small consented pilot: did students understand the result, try an activity, and find the next step helpful?

Universities remain a small static research catalog and weekly digest delivery is unimplemented. Prioritize the assessment-to-activity journey over increasing feature count. Analytics code does nothing until configured; do not claim measured conversion or retention from the presence of event calls alone.

## Recommended order

1. Correct neutral/weak-signal outputs and clarify reasoning's role in rankings.
2. Verify account recovery and a real backup restore.
3. Complete outstanding authenticated, account-lifecycle and school-load checks.
4. Bring localized guide content to the intended level and simplify assessment entry copy.
5. Run a supervised pilot and use observed comprehension, activity completion and return usage to guide the next changes.

## Self-review and implementation — 13 October

The neutral-label finding is a reproduced correctness defect. The ranking finding is a mathematical property of the formula, not by itself proof that a different model would be better. My original recommendation could have been read as permission to replace weights without validation; that would be unjustified. No new scoring weights or arbitrary weak-signal threshold were introduced.

Likewise, saying the site is ready for a pilot is a judgment based on a limited review, not certification of current production security, educational outcomes or consent compliance. The localized-guide finding measures a content difference, not measured student satisfaction. Operational findings come partly from earlier release records, not a fresh database audit.

Implemented changes:

- Exact ties become open `X` axes, with Mixed preferences in results/dashboard and translated explanations. Dependent styles and personality strengths are suppressed; partial ties retain evidence on other axes. The cognitive profile becomes neutral Exploring when the personality is unresolved.
- New saves use `v3`. Historical scores and rankings are preserved. An idempotent retry derives recommended skills from the returned saved row rather than the newly computed profile.
- The unchanged reasoning formula is explained in English, Russian and Uzbek on methodology/results pages, including the common score shift and profile thresholds.
- Seventeen curated guide careers now have Russian/Uzbek work descriptions, skills and specific safe practice activities. Salary, exam and university requests retain separate cautious branches. This does not claim full language parity for every conversational intent or all 166 careers.
- Assessment introduction is shorter; optional instructions live under Before you start. Account requirements remain visible before answering.
- Neutral-answer, partial-tie and multilingual-career regressions are covered by tests.

No database migration is required by these code changes. Email recovery remains gated until an owned sender and real delivery are verified. A code push cannot prove a backup restoration, enable verified SMTP or replace a consent review. Those operations remain open; this implementation does not claim they were completed.
